# SolidityScan repository scan (2026-10-31)

SolidityScan scanned the repository `armanalabsai/arlcoin.io` on 2026-10-31. It reported:

- a security score of 54.52/100 over 9,921 lines and 1,434 issues;
- a threat score of 64/100: 0 high, 3 moderate, 3 low, 11 no impact, 6 beneficial and 13
  unavailable.

An earlier scan of the token contract alone scored 93.70: 0 critical, high, medium or low, 19
informational and 15 gas.

This note records what each group of results refers to and what was done about it.

Results in the generated verifier, the scripts, the tests and the libraries do not describe
deployed code. The verifier is checked in CI (`zk/check.sh`) to match Barretenberg's output exactly,
so it is not edited by hand.

## Why the code itself is not rewritten

The contracts in `contracts/src` are deployed on Base Mainnet and cannot be upgraded. The token,
vesting wallets and timelock are live; the jobs escrows and evaluators are at deployer nonces 23 to 26. Each is source-verified (Sourcify exact match).

The source is what the 2026-10-17 internal audit and the 2026-10-28 external audit reviewed.
`npm run check:bytecode` fails CI if the build no longer reproduces the recorded bytecode. A change
to the code would therefore:

- produce contracts that are no longer the ones deployed and verified;
- reopen the audit;
- buy at most a few hundred gas per call on Base.

The gas results below are recorded and not applied. The documentation results are applied, because
NatSpec comments do not change the bytecode: `bytecode_hash = "none"` and `cbor_metadata = false`
in `contracts/foundry.toml`.

## Gas results (not applied)

These results are compiler-level micro-optimisations that do not affect correctness or safety:

- unchecked arithmetic
- storage variable caching
- splitting revert or require statements
- payable constructors
- `++i`
- cheaper inequalities
- packing similar data types
- zero-to-one storage writes
- array length caching
- public constants
- inlined functions
- named returns
- Solady instead of OpenZeppelin

Two reasons they are not applied:

- **Checked arithmetic and OpenZeppelin are deliberate.** Solidity 0.8 checked arithmetic and
  OpenZeppelin's audited implementations are kept on purpose; replacing them with unchecked
  blocks or another library adds risk for little gas.
- **A payable constructor would accept ETH.** Making a constructor payable lets the deployment
  carry ETH, which no ARL contract can return.

## Informational results

| Result                                                                            | Where                                                                           | Status                                             |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------- |
| Missing `@title`/`@author`/`@notice`/`@dev`/`@param`/`@return`                    | Interfaces and contract headers in `src`                                        | Added in this change (bytecode unchanged)          |
| In-line assembly; assembly calls                                                  | Generated verifier; one bounded `staticcall` in `ARLVerifiedEvaluator._ownedBy` | By design (see below)                              |
| Contract name casing, unused imports, unused variables, unused internal functions | Scripts, tests, libraries                                                       | Not deployed code                                  |
| Default values set explicitly, superfluous event fields                           | `src`                                                                           | Kept: events match ERC-8183 and the app's indexers |

`ARLVerifiedEvaluator` reads the ERC-8004 identity registry's `ownerOf` with a `staticcall` in
assembly. The call:

- caps the gas it forwards (`REGISTRY_GAS`);
- copies at most 32 bytes of return data;
- treats a short or failed reply as "not the owner".

A reverting or gas-heavy registry therefore cannot block a vote or settlement.

## Threat scan results

| Result                                                                      | What it refers to                                                                                                                                        | Assessment                                                                                                                                                                |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Malicious typecasting" (uint160 to address)                                | `ARLVerifiedEvaluator._ownedBy` compares the registry's returned word with `uint256(uint160(account))`                                                   | A comparison, not a cast that creates an address. Correct ABI decoding of an `address` return value                                                                       |
| "Functions having totalSupply update"                                       | OpenZeppelin `ERC20._update`, called by `_mint`                                                                                                          | `ARLToken` mints the fixed 21,000,000 ARL once, in the constructor. It has no mint or burn function, and `totalSupply()` equals `MAX_SUPPLY` for the life of the contract |
| "Functions having addresses with special access" and "owner-only functions" | Per-job roles in `ARLJobs`; `rewardsDistribution` in `ARLStakingRewards`; `arbiter` in `ARLVerifiedEvaluator`; `VestingWallet`'s owner (the beneficiary) | Each role is fixed at deployment (immutable) and bounded (details below)                                                                                                  |
| "Hardcoded addresses"                                                       | `SLASH_SINK = 0x…dEaD` in `ARLVerifiedEvaluator`                                                                                                         | Slashed bonds are burned to a fixed address on purpose, so no one, including the arbiter, can receive them                                                                |
| "Can be compiled with a more recent Solidity version"                       | `pragma solidity 0.8.36`                                                                                                                                 | The compiler is pinned so the build reproduces the deployed bytecode exactly. Changing it would change the bytecode                                                       |

The privileged roles in detail:

- **Per-job roles in `ARLJobs`:** client, provider and evaluator. These are the parties of each
  job, as ERC-8183 specifies.
- **`rewardsDistribution` in `ARLStakingRewards`:** can only fund a reward period, set its length
  (at most one year) and return unallocated rewards after a period ends.
- **`arbiter` in `ARLVerifiedEvaluator`:** a 2-of-3 Safe that rules only on disputed jobs, can
  only pay the escrow to the client or the provider, and never receives slashed bonds.
- **`VestingWallet`'s owner:** the beneficiary, who receives the vested tokens and can
  hand the role to another address; the schedule itself cannot change.
- **No admin powers:** no contract has an owner who can mint, pause, upgrade, change balances or
  set fees.

The threat scan's own positive results match this:

- no hidden owner;
- tokens cannot be burned (no burn function);
- no proxy or upgrade;
- no owner-controlled balance changes;
- no cooldown;
- not vulnerable to the ERC-20 approve race condition.
