# x402-arl-upto v0.1.0

Status: **draft**, 2026-10-24. Reference implementation: [`packages/payments`](../../../packages/payments)
(`@arl/payments` 0.1.0). Conformance vectors: [`vectors.json`](vectors.json), generated by
[`generate-spec-vectors.ts`](../../../packages/payments/scripts/generate-spec-vectors.ts) and replayed in CI by
[`packages/payments/test/spec-vectors.test.ts`](../../../packages/payments/test/spec-vectors.test.ts).

This document profiles the x402 v2 `upto` scheme for metered payments to AI and compute services,
and adds one thing upto does not have: a **signed usage receipt** that makes the settled amount a
checkable claim of the service. The key words MUST, MUST NOT, SHOULD and MAY are as in RFC 2119.

## 1. Scope and roles

- **Payer**: the agent or user that signs a payment authorization.
- **Service** (payee): the HTTP resource that answers `402 Payment Required`, does the work and
  meters it.
- **Facilitator**: verifies the authorization and settles on chain through the x402 upto proxy.
- **Receipt signer**: the key the service uses to sign usage receipts (MAY be the payee address).

Out of scope for v0.1.0: verification of the work itself (see section 10), refunds after
settlement, and any network other than those in section 2.

## 2. Networks and pinned contracts

| Network      | CAIP-2         | Permit2                                      | x402 upto proxy                              |
| ------------ | -------------- | -------------------------------------------- | -------------------------------------------- |
| Base Sepolia | `eip155:84532` | `0x000000000022D473030F116dDEE9F6B43aC78BA3` | `0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002` |

A facilitator MUST compare the runtime code hash of both contracts with the pinned hashes
(`packages/payments/src/networks.ts`, `assertPinnedCode`) before its first settlement and MUST
refuse any other network. Base Mainnet (`eip155:8453`) is reserved for v0.2.0.

## 3. Payment requirements

A service answers `402` with x402 v2 `PaymentRequirements`:

| Field               | Rule                                                                       |
| ------------------- | -------------------------------------------------------------------------- |
| `scheme`            | MUST be `"upto"`.                                                          |
| `network`           | MUST be a network of section 2.                                            |
| `asset`             | MUST be the pinned payment token of that network.                          |
| `amount`            | The **ceiling**, in base units, decimal string, MUST be > 0.               |
| `payTo`             | The payee; MUST NOT be the zero address.                                   |
| `maxTimeoutSeconds` | Integer, MUST be between 30 and 600.                                       |
| `extra`             | MUST contain `facilitatorAddress` (non-zero); MAY contain `usageReceipt`.  |

Reference: `buildUptoRequirements`.

## 4. Authorization

The payer signs a Permit2 `PermitWitnessTransferFrom` as defined by the x402 upto scheme. The
fields a facilitator reads (`Permit2Authorization`):

| Field                                  | Rule                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| `from`                                 | The payer.                                                  |
| `spender`                              | MUST be the pinned x402 upto proxy.                         |
| `nonce`                                | Permit2 nonce; with `from` and the chain it is the key.     |
| `deadline`                             | Unix seconds; MUST be in the future and at most 600 s away. |
| `permitted.token`, `permitted.amount`  | MUST equal `asset` and the ceiling.                         |
| `witness.to`, `witness.facilitator`    | The payee and the facilitator, bound by the signature.      |
| `witness.validAfter`                   | Unix seconds before which settlement is invalid.            |

## 5. Metering

`amount = min(units × unitPrice, ceiling)`, integer arithmetic in base units. `units` and
`unitPrice` MUST NOT be negative. Reference: `meter`. Vectors: `meter`.

## 6. Settlement rules

Before sending a settlement of `amount` under an authorization, a facilitator MUST, in order:

1. refuse if the authorization key (`chainId:from:nonce`) was already used, in any state;
2. refuse if `amount` exceeds the ceiling;
3. refuse if the deadline has passed, or is more than 600 seconds away;
4. if `amount` is 0, retire the key without a transaction;
5. otherwise record the key as `settling` **before** sending, then `settled` or `failed`.

A failed settlement is never retried with the same authorization. Reference: `decideSettlement`,
`ArlUptoFacilitator.settle`. Vectors: `settlement`.

## 7. Usage receipts

For every charged call the service signs an EIP-712 receipt:

- Domain: `{ name: "ARL Usage Receipt", version: "1", chainId }`.
- Type `UsageReceipt(address payer, address payTo, address token, uint256 nonce, uint256
  ceiling, uint256 deadline, bytes32 resource, uint256 units, uint256 unitPrice, uint256 amount,
  bytes32 response)`.
- `resource` = keccak256 of the UTF-8 resource identifier; `response` = keccak256 of the exact
  response bytes delivered.
- Wire form: `{ receipt: { …all fields as strings… }, signature }`; integers as decimal strings.

When a payee has a pinned receipt signer, the facilitator MUST settle only an amount backed by a
valid receipt (`extra.usageReceipt`). A receipt is valid for a settlement when all hold:
signed by the pinned signer; `payer`, `payTo`, `token`, `nonce`, `ceiling`, `deadline` equal the
authorization; `amount` equals the amount settled; `amount = min(units × unitPrice, ceiling)`;
and, on the payer's side, `response` covers the bytes received. Reference: `checkUsageReceipt`.
Vectors: `receipt`.

A receipt makes a charge attributable and reproducible; it does **not** prove the units were
really consumed.

## 8. Errors

Facilitator `invalidReason` / `errorReason` values: `arl_scheme`, `arl_network`, `arl_asset`,
`arl_spender`, `arl_receipt: <problems>`, `arl_policy: <reason>`, plus the x402 SDK's own.

## 9. Security considerations

- Replay: one authorization settles at most once (section 6, step 1 and 5).
- Over-charge: bounded by the ceiling on chain and by the receipt off chain.
- Long-lived authorizations: capped at 600 seconds.
- Front-running a settlement: the witness binds payee and facilitator.
- Receipt-signer compromise: the payer's loss is still bounded by each ceiling.

## 10. Reserved: verified mode (v0.2.0)

v0.2.0 is planned to add `scheme: "arl-escrow"`: the authorization funds an ERC-8183 job in
`ARLJobs` instead of paying the service, and `ARLVerifiedEvaluator` releases it after a staked
committee re-executes the work (`docs/reexecution-spec.md`) and the challenge window passes.
Non-normative until then.

## 11. Versioning and conformance

SemVer. A change that alters any vector's expected result is a breaking change and needs a new
major (or, before 1.0.0, minor) version. An implementation conforms to v0.1.0 when it reproduces
every result in `vectors.json`.
